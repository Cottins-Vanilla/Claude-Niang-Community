# 版本号规则

版本号有两种格式：

- **正式版** `X.Y.Z`，三段都是没有前导零的整数，例如 `2.1.0`。
- **测试版** `X.Y.Z-beta.N`，例如 `2.1.0-beta.6`，`N` 从 1 开始，规则见下文「测试版」。

除了 `-beta.N`，不加 `-rc.1`、`-repack.1` 之类的后缀，发布工作流会拒绝这类标签。

## 命名

同一个版本在各处的写法如下，版本号部分必须完全一致：

| 位置 | 正式版 | 测试版 |
|---|---|---|
| `package.json`、扩展 `manifest.json` 的 `version` | `2.1.0` | `2.1.0-beta.6` |
| Git 标签 | `v2.1.0` | `v2.1.0-beta.6` |
| 发布页标题（工作流生成） | `Claude 娘社区版 v2.1.0 · Windows` | `Claude 娘社区版 v2.1.0-beta.6 · Windows（测试版）` |
| 安装包（工作流生成） | `claude-niang-v2.1.0-windows.zip` 和同名 `.sha256` | `claude-niang-v2.1.0-beta.6-windows.zip` 和同名 `.sha256` |
| 桌面扩展附件 | `claude-niang-usage.mcpb` | `claude-niang-usage.mcpb` |
| CHANGELOG 章节标题 | `## 2.1.0 — YYYY-MM-DD` | `## 2.1.0-beta.6 — YYYY-MM-DD` |
| 准备发布用的分支 | `release/2.1.0` | `release/2.1.0-beta.6` |
| README 当前版本、徽章、下载链接 | 改成 `2.1.0` / `v2.1.0` | **不改**，继续写最新正式版 |
| GitHub 上的状态 | 正式发布，高于当前最新版时成为 Latest | 预发布，不成为 Latest |

标签和附件都由发布工作流创建，不要提前手动创建。

## 正式版的各段

| 位置 | 含义 | 什么时候变 |
|---|---|---|
| X | 正式版号 | 基本不变。社区版从 `2.0.0` 起步。只有用户明确决定时才改，不要主动提议 X+1。 |
| Y | 小版本 | 新增功能或较大改动时 +1，同时 Z 归零。例如 `2.0.3` → `2.1.0`。 |
| Z | 修复版本 | 修复 bug、做简单维护时 +1。例如 `2.1.0` → `2.1.1`。 |

## 判断步骤

1. 先运行 `git fetch --tags`，拿到最新的标签。
2. 找到上一个**正式版**标签（排除测试版）：

   ```powershell
   git describe --tags --abbrev=0 --match "v*" --exclude "*-beta.*"
   ```

   不加 `--exclude` 时，找到的可能是测试版标签，会漏算前面几个测试版的改动。
3. 列出它之后要发布的全部改动：`git log --oneline <上一个正式版标签>..HEAD`，再对照 CHANGELOG 的「未发布」章节和其间各测试版的章节。必要时看 `git diff --stat <上一个正式版标签>..HEAD`。
4. 逐项归类：

   **算 Y（新功能或较大改动）**
   - 用户能看到的新功能：新窗口、新页面、新菜单项、新设置项。
   - 现有功能的行为明显改变，例如读取额度的时机、开机启动方式、数据保存位置、默认设置。
   - 数据格式改变、旧数据需要迁移，或用户需要重新安装、重新登录、重新装桌面扩展。
   - 较大的重构、更换依赖、提高最低 Windows / Node.js / WebView2 要求。
   - 桌面扩展新增工具，或工具的返回内容改变。

   **算 Z（修复、简单维护）**
   - 修复 bug、崩溃、显示错误、错别字。
   - 不改变用法的小调整：性能、日志、错误提示措辞、界面细节。
   - 文档、测试、CI 和依赖的小版本更新。
   - 修复安全问题或杀毒软件误报，只要用户的用法不变。

5. 合并判断：**只要有一项算 Y，整个版本就按 Y 递增（Y+1，Z 归零）**，以大的为主。全部是 Z 类改动时才 Z+1。
6. **无法抉择时，先问用户。**写清楚有争议的是哪几项改动、分别像 Y 还是像 Z、你建议哪个版本号，等用户决定后再改文件。常见的拿不准的情况：
   - 改动很小，但用户能看见，比如只加了一个菜单项。
   - 修 bug 的同时改变了原有行为。
   - 只有文档或仓库维护的改动，要不要单独发一版。

## 测试版

想让一部分人先试新功能时，可以发测试版：`X.Y.Z-beta.N`。

- `X.Y.Z` 是**下一个正式版**的版本号，按上面的步骤判断。
- `N` 从 1 开始，同一个正式版的测试版依次 +1：`2.1.0-beta.1` → `2.1.0-beta.2`。找当前最新的测试版：

  ```powershell
  git tag -l "v2.1.0-beta.*" --sort=-v:refname
  ```

  第一行就是最新的，下一个测试版的 `N` 是它加 1。
- 测试版排在同号正式版之前：`2.1.0-beta.2` < `2.1.0`。测试完成后发 `2.1.0` 正式版，不要再给 `2.1.0` 发测试版。
- 测试中途发现改动该算到更大的版本（例如已经在发 `2.0.1-beta.N`，后来加了新功能），后面的测试版直接用新的号，从 `beta.1` 重新开始，例如 `2.1.0-beta.1`；已发的测试版保留不动。
- 测试版在 GitHub 上标为“预发布”，不会成为 Latest；挂件里「更新范围」选「测试版」的用户才会收到提醒。
- 发测试版要同步 `package.json`、扩展 `manifest.json` 和 CHANGELOG 的 `## X.Y.Z-beta.N — YYYY-MM-DD` 章节；**README 的版本号、徽章和下载链接不改**，它们始终指向最新的正式版。

## 用户只说「发布」时

用户要求发布但没说版本号、也没说测试版还是正式版时，不列选项让用户挑，按下面自己定，然后直接整理发布说明（仓库根目录的 CLAUDE.md 也这样要求）：

1. 先运行 `git fetch --tags`，看最新的标签。
2. 最新的标签是测试版 `X.Y.Z-beta.N`，并且还没有发 `X.Y.Z` 正式版：发下一个测试版 `X.Y.Z-beta.(N+1)`。
   - 例外：这次的改动按判断步骤要升到比 `X.Y.Z` 更大的版本（例如测试版是 `2.0.1-beta.N`，又加了新功能），就按「测试版」一节换新号，从 `beta.1` 开始。
3. 最新的标签是正式版：按判断步骤定下一个正式版号，直接发正式版。
4. 用户明确说了「测试版」「正式版」或具体版本号时，照用户说的做。
5. 只有判断步骤里拿不准 Y 还是 Z、或者涉及改 X 时，才问用户。问的时候只问版本号这一件事，写明你的建议。

不管哪种情况，触发发布流程之前都要把最终的发布说明全文给用户看，得到确认后再发布（见 `release-page` skill）。

## 从测试版到正式版

同一个 `X.Y.Z` 的测试版都测完后，发 `X.Y.Z` 正式版：

- CHANGELOG 新增一个 `## X.Y.Z — YYYY-MM-DD` 章节，写**上一个正式版以来的全部改动**，也就是把各测试版和「未发布」的内容合在一起：
  - 同一件事前后改过几次的，只写最终结果；中途加了又撤掉的不写。
  - 只在测试版之间出现、正式版用户碰不到的问题（例如 beta.2 引入、beta.3 修好的 bug），不写进「修复」。
  - 概括句不写「测试版」；「更新方法」不写测试版提醒那一段。
  - 「已知问题」重新核对：测试中已经验证的删掉，还没验证的照实保留。
- 各测试版的章节**保留**在正式版章节下面，作为历史记录，不删除、不改写。
- README 这时才更新：当前版本、徽章、“本版……”说明、版本说明链接和下载链接都换成 `X.Y.Z`；功能说明与正式版保持一致。
- 正式版的版本号仍按上面的判断步骤，和上一个**正式版**比较，不和测试版比较。

## 其他规则

- 已经公开的版本号不能再用，测试版也一样。发布后发现问题，修好后发下一个版本。已公开的标签和附件不覆盖、不移动、不删除。
- 版本号只增不减，也不跳号：`2.1.0` 之后只能是 `2.1.1` 或 `2.2.0`；`2.1.0-beta.2` 之后是 `2.1.0-beta.3` 或 `2.1.0`（改动升级到更大的版本时，按「测试版」一节换成新的号）。
- 版本号定下后，在同一次提交里同步修改下面这些位置：
  - `claude-niang/package.json` 的 `version`
  - `claude-niang/extension/manifest.json` 的 `version`
  - CHANGELOG：把「未发布」改成唯一的 `## X.Y.Z — YYYY-MM-DD` 或 `## X.Y.Z-beta.N — YYYY-MM-DD` 章节，正文格式见 `release-page` skill
  - **仅正式版**：README 的 `**当前程序版本：X.Y.Z**`、版本徽章、“本版……”一句话说明、版本说明链接和附件下载链接（标签和 ZIP 文件名都要换成新版本）
- 改完运行下面的检查，通过后再提交（测试版也一样，标签写完整，例如 `v2.1.0-beta.6`）：

  ```powershell
  node tools/release.mjs --source . --check-release --tag vX.Y.Z
  ```

- 提交和推送按 `commit-hygiene` skill 做；发布按 `release-page` skill 做。
